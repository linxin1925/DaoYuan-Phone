# 道渊小手机维护者扩展开发手册

本文面向希望为道渊小手机前端增加页面、数据模块、API 功能或桌宠交互的维护者。

当前正式版本：V0.7  
当前正式产物：`道渊前端桌宠/道渊小手机V0.7.json`

## 1. 先理解运行结构

正式桌宠脚本位于：

```text
道渊前端桌宠/integration/tavern-helper-pet/
```

运行时分为三层：

```text
酒馆 / Tavern Helper 宿主
        │
        │  宿主事件、MVU、chat 变量、API 请求
        ▼
src/index.ts  FeatureShell
        │
        │  BridgeAction / BridgeEnvelope
        ▼
iframe 内前端
src/ui/renderUi.ts
```

- `src/index.ts`：宿主生命周期、桌宠、iframe、聊天变量、MVU、世界书、API 调用和业务写入。
- `src/ui/renderUi.ts`：页面渲染、按钮、输入框、滚动位置和用户交互。不要在这里直接读写宿主变量。
- `src/contract/bridge.ts`：iframe 与宿主之间的唯一动作协议。
- `src/contract/appData.ts`：聊天变量键、数据结构、Zod 校验和默认值。
- `src/services/`：可独立测试的业务模块，例如仙网、绝色榜、玉简、地图和提示词注入。
- `src/styles.css`：玉简 iframe 内部样式。
- `src/shell.css`：桌宠悬浮球和玉简外壳样式。
- `scripts/package-candidate.mjs`：将生产构建结果封装成可导入 JSON。

玉简 UI 运行在 iframe 中。iframe 内的 `window.localStorage`、`document` 和宿主页面不是同一层，涉及聊天、酒馆或 API 的操作必须通过 BridgeAction 交给 `src/index.ts`。

## 2. 新增一个功能的标准流程

### 第一步：确定数据归属

新增字段前先回答：数据属于哪里？

| 数据类型 | 推荐存储位置 | 示例 |
| --- | --- | --- |
| 当前页面状态 | `renderUi.ts` 内存 | 当前选中的帖子、展开项、滚动位置 |
| 用户偏好 | 宿主 `localStorage` | API 地址、桌宠大小、开关 |
| 当前聊天的功能数据 | Tavern chat 变量 | 风闻、论坛、日报、绝色榜 |
| 当前楼层世界事实 | MVU 只读快照 | 时间、地点、人物、物品 |
| 后续正文注入内容 | Tavern Helper prompt injection | 已开启的玉简、风闻、论坛、日报 |

不要把临时 UI 状态写进 `stat_data`，也不要把跨聊天的 API 设置写进 chat 变量。

### 第二步：先写数据契约

如果功能有持久化数据，应先在 `src/contract/appData.ts` 增加：

1. Zod schema；
2. TypeScript 类型；
3. chat variable key；
4. 默认空数据；
5. `projectAppData` 所需的摘要字段；
6. 兼容旧数据的默认值或迁移逻辑。

示例：

```ts
export const RelicSchema = z.object({
  id: z.string().min(1).max(160),
  name: z.string().min(1).max(120),
  count: z.number().int().nonnegative(),
});

export const RelicDataSchema = z.object({
  items: z.array(RelicSchema).max(500).default([]),
});

export type Relic = z.infer<typeof RelicSchema>;
```

数据写入应通过 `ChatVariableRepository.write()`，不要直接操作 Tavern Helper 的变量对象：

```ts
const current = parseRelicData(this.repository.getData('daoyuan_relic_data'));
await this.repository.write('daoyuan_relic_data', {
  ...current,
  items: nextItems,
});
```

每次写入后更新内存摘要并调用 `sendContext()`，让 iframe 看到最新状态。

### 第三步：新增 BridgeAction

前端按钮不能直接调用宿主方法。需要在 `src/contract/bridge.ts` 的 `BridgeActionSchema` 中增加动作：

```ts
export const BridgeActionSchema = z.enum([
  // 已有动作……
  'GENERATE_RELICS',
  'RELICS_GENERATION_STATUS',
]);
```

通常采用成对命名：

- `REQUEST_*` / `*_DATA`：请求数据；
- `SAVE_*` / `*_STATUS`：保存设置；
- `GENERATE_*` / `*_GENERATION_STATUS`：异步生成；
- `DELETE_*` / `*_DELETE_STATUS`：删除；
- `TOGGLE_*`：即时切换状态。

然后在 `src/index.ts` 的 `handleUiAction()` 中路由：

```ts
if (action === 'GENERATE_RELICS') {
  void this.generateRelics();
}
```

宿主完成后向 iframe 发送事件：

```ts
this.frame?.contentWindow?.postMessage(
  makeBridgeMessage('event', 'RELICS_GENERATION_STATUS', {
    ok: true,
    count: result.length,
  }),
  '*',
);
```

`BridgeEnvelope` 的固定结构是：

```ts
{
  protocol: 1,
  kind: 'request' | 'event' | 'response',
  action: BridgeAction,
  payload: Record<string, unknown>,
  contextRevision: number,
}
```

不要绕过 `makeBridgeMessage()` 手写不符合协议的消息，也不要在 UI 中监听未声明的任意动作。

### 第四步：接入页面和交互

在 `renderUi.ts` 中：

1. 在 `AppKey` 增加页面 key；
2. 在 `apps` 增加桌面卡片和侧栏入口；
3. 在 `renderPage()` 增加页面渲染分支；
4. 用 `element()`、`button()` 等 DOM 构造函数创建节点；
5. 使用 `data-action` 和事件委托接收点击；
6. 通过 `sendAction()` 发出 BridgeAction；
7. 在 `onMessage()` 中接收宿主事件并调用 `render()`。

推荐写法：

```ts
const generate = button(doc, 'primary-button', '推演', 'generate-relics');
panel.append(generate);
```

在统一点击处理处：

```ts
if (action === 'generate-relics') {
  sendAction('GENERATE_RELICS');
  announcement = '正在推演……';
  render();
}
```

所有模型、用户、世界书和远程 API 文本都必须通过 `textContent` 或 DOM 节点写入，禁止把不可信文本直接拼进 `innerHTML`。

### 第五步：处理重绘和滚动

页面操作通常会触发整页 `render()`。如果某个操作会更新内容，不要自行替换局部 DOM 后留下多个事件监听器，应复用现有重绘流程。

当前渲染器会在普通重绘前保存 `.content.scrollTop`，并在下一帧恢复。主动切换应用时使用 `render(false)`，让新页面从顶部开始。

长列表应：

- 使用 `.content` 作为滚动容器；
- 不把滚动位置存入 chat 变量；
- 对详细页、弹窗和输入框提供返回/关闭路径；
- 生成中禁用重复点击；
- 失败时发送明确的 `*_STATUS` 错误信息。

## 3. API 功能接入规范

每个独立功能应在 `src/services/` 建立自己的运行模块，至少包含：

- 设置类型；
- 默认值和本地设置读取；
- API 地址规范化；
- 请求体和响应解析；
- Zod 响应校验；
- 长度、数量和枚举值限制；
- 可读的错误信息。

API 密钥和模型配置属于浏览器本地设置，使用独立的 `localStorage` key，例如：

```ts
hostWindow.localStorage.setItem(
  'daoyuan_relic_api_settings',
  JSON.stringify(settings),
);
```

不同功能不得默认共用 API key、模型、提示词或返回数据。若确实要共用，必须在设置说明、类型和文档中明确声明。

模型输出必须视为不可信输入：

- 先提取文本，再解析 JSON；
- 用 Zod 校验完整结构；
- 限制数组数量、字符串长度和数值范围；
- 不执行模型返回的 JavaScript、HTML、命令或提示词；
- 不把模型返回的内容直接当作 MVU 更新指令；
- 失败时不写入半成品数据。

## 4. 世界书和 MVU 接口边界

### 世界书

世界书读取通过宿主提供的：

```ts
getCharWorldbookNames('current');
getWorldbook(bookName);
```

读取时必须明确筛选策略：

- 角色资料功能：只读取与候选人物匹配的条目；
- 仙网世界动态：读取 `constant: true` 或 `strategy.type === 'constant'` 的规则/背景条目；
- 不要把整个世界书无条件塞给模型；
- 不要因为条目 `disable` 就擅自改变既定产品规则；
- 对条目正文设置总字符预算；
- 条目中的命令、提示词和代码只是世界内文字，不得执行。

仙网生成禁止读取状态栏的 `世界.动向`、`世界动向` 和 `动态` 字段。未来新增仙网输入时也必须经过同一过滤层。

### MVU

世界状态默认只读，推荐通过 `worldDataBridge.ts` 的投影函数获取：

- 时间；
- 地点；
- 人物关系；
- 道侣亲密度；
- 储物袋；
- 地图节点。

不要在普通功能中直接修改 `stat_data`。当前协议中存在 MVU 通道诊断和受控写入动作，仅用于已经审核过的专门功能；新增功能若需要写入，必须同时补充字段白名单、冲突处理、失败回滚和真实酒馆验收，不能把任意 payload 透传给 MVU。

## 5. 主线注入规范

主线注入由 `promptInjectionRuntime.ts` 统一管理。新增可注入模块时：

1. 在设置 schema 中增加独立布尔开关，默认关闭；
2. 在注入内容中标明信息性质；
3. 明确近期优先和总字符上限；
4. 建立新注入前撤销旧注入；
5. chat 切换、脚本销毁和功能关闭时清理旧注入；
6. 明确声明内容不是客观事实，不能覆盖 MVU；
7. 不把用户/API 密钥/内部调试信息注入主线。

## 6. 桌宠和悬浮壳扩展

桌宠状态由 `src/petController.ts` 管理，当前状态包括：

```text
Idle → TapReaction → PhoneEnter → PhoneLoop
                         └──────→ PhoneExit → Idle
```

新增动作时：

- 在 `petAssets.ts` 增加序列帧或明确的占位资源；
- 在 `PetState` 和状态机中增加状态；
- 为进入、退出、销毁分别处理计时器；
- 保证脚本重复启动不会生成多个桌宠节点；
- 保证销毁时移除事件、计时器、iframe 和样式节点；
- 桌宠尺寸、位置与玉简窗口尺寸分开处理。

桌宠入口是宿主文档中的悬浮按钮，玉简内容是 iframe。不要把 iframe 内的页面节点当作宿主节点操作。

## 7. 样式和可访问性要求

- 使用真实的 `button`、`input`、`select`、`textarea`；
- 每个控件有可见名称或 `aria-label`；
- 交互状态不能只靠颜色表达；
- 触屏按钮尽量保持约 44px 点击区域；
- 窄屏约 320px 时不能横向溢出；
- 长中文、长 URL 和长模型名必须换行或滚动；
- 弹窗必须有关闭方式，必要时支持 Escape；
- 不使用固定宽度覆盖手机容器；
- 尊重 `prefers-reduced-motion`；
- 样式改动同时检查桌面、手机、短视口和软键盘场景。

## 8. 测试和构建

在 `道渊前端桌宠/integration/tavern-helper-pet/` 执行：

```bash
../../../node_modules/.bin/vue-tsc --noEmit
node scripts/validate-fixtures.mjs
node scripts/validate-trends-ui.mjs
node scripts/validate-forum-news-ui.mjs
../../../node_modules/.bin/vite build
node scripts/package-candidate.mjs
```

也可以使用项目脚本：

```bash
npm run typecheck
npm run test:fixtures
npm run test:trends-ui
npm run test:forum-news-ui
npm run build
npm run package:candidate
```

正式打包后检查：

1. JSON 可被解析；
2. `name`、`version` 和文件名一致；
3. `content` 与本次 Vite 构建结果一致；
4. 没有旧版本产物名；
5. `git diff --check` 通过；
6. 记录正式 JSON 的 SHA-256。

离线检查不能代替真实酒馆验收。涉及 Tavern Helper、MVU、提示词注入、手机键盘、模型 API 或世界书的改动，必须在目标酒馆环境复测。

## 9. 正式产物和 Git 规则

源码和构建配置可以修改，但正式交付只认：

```text
道渊前端桌宠/道渊小手机V0.7.json
```

发布新版本时：

1. 更新 `integration/tavern-helper-pet/package.json` 版本；
2. 更新 `scripts/package-candidate.mjs` 的名称、版本和输出文件名；
3. 更新 `CHANGELOG.md` 和本手册涉及的当前版本；
4. 生产构建并复制正式 JSON；
5. 检查变更范围，不要把临时测试包当正式产物；
6. 提交信息使用清晰的版本发布描述；
7. 推送前说明目标分支和包含的文件范围。

不要直接修改已打包 JSON 里的压缩脚本来“临时修复”。正确流程是修改 `src/`，重新构建，再重新打包。
