## 1. 开工三格

### 1.1 目标

在 V0.8 全部功能不回退的前提下，为玉简新增“万宝商行”：

- AI 按道渊世界观生成可购买商品；
- 用户可配置自动更新、更新间隔、单轮商品数和保留上限；
- 读取并固定展示极品、上品、中品、下品四档灵石余额；
- 兼容原版卡“灵石混在储物袋”和战斗版“四档灵石为主角直属字段”两种结构；
- 支持购买与出售，并在同一次受控 MVU 写回中完成货币和资产变化；
- 交易后复读同一楼层，实时同步小手机余额、储物袋和器物。

本版本不修改角色卡、世界书、MVU schema 或变量更新规则。

### 1.2 红线

- 不覆盖或重打 `道渊小手机V0.8.json`。
- 不基于当前 `ziwei-live2d` / V1.5 预览源码开发。
- 不从仓库根目录旧源码重建。
- 不删除、移动或提交 PSD、素材、V1.5 文件及其他无关改动。
- 未经确认不推送 GitHub，不发布正式 V0.9。
- 不读取或修改 `stat_data` 中未授权的业务字段。
- 不允许 AI 返回或决定 MVU 路径、变量补丁、余额变更或交易结果。
- 不对候选灵石执行模糊扣款；候选必须由用户确认映射。
- 不自动跨品级兑换或找零，除非后续取得明确世界书规则与单独确认。
- 不把本地缓存、chat 变量或 UI 显示值当作玩家资产真源。

### 1.3 验收

- V0.8 既有类型检查、fixture、UI 合约和专项回归全部通过。
- 新增 V0.9 商行/交易回归和 UI 合约通过。
- 生产构建通过，V0.9 测试 JSON 的 `content` 与构建 JS 字节一致。
- V0.8 正式 JSON hash 不变。
- 原版与战斗版真实 SillyTavern 分别完成余额、购买、出售、刷新、重 Roll、切 chat 验收。
- 每次交易只改授权路径；复读证明未授权字段不变。
- UI 成功必须以可见结果、computed style、尺寸及实际截图共同确认。

## 3. 数据所有权和授权范围

### 3.1 MVU 允许读取和修改

```text
stat_data.主角.储物袋
stat_data.主角.器物

# 战斗版货币的唯一例外
stat_data.主角.极品灵石
stat_data.主角.上品灵石
stat_data.主角.中品灵石
stat_data.主角.下品灵石
```

除上述路径外，万宝商行不得读取或修改其他业务字段。为安全提交可以克隆并保留完整 `stat_data` 外壳，但商行业务逻辑不得消费或变更其他字段。

### 3.2 商行自管数据

新增 chat 变量建议命名：

```text
daoyuan_wanbao_data
```

保存当前聊天的商品、自动更新元数据和交易展示记录。API 设置与货币适配偏好保存在宿主 localStorage，API key 不进入 chat 变量。

建议契约：

```ts
interface WanbaoData {
  schemaVersion: 1;
  items: WanbaoItem[];
  autoCounter: number;
  processedMessageIds: string[];
  processedSwipeKeys: string[];
  triggeredMessageIds: string[];
  triggeredSwipeKeys: string[];
  transactionReceipts: TransactionReceipt[];
}
```

交易记录只用于显示和诊断，不得作为余额或物品真源。

## 4. 功能契约

### 4.1 万宝商行页面

桌面新增“万宝商行”应用，至少包含：

- 四档灵石余额固定栏；
- 商品列表与分类筛选；
- 商品详情和购买确认；
- “出售”页签，分别列出储物袋与器物；
- 设置入口；
- 最近交易结果，不展示敏感调试数据。

四档余额卡片始终存在，缺失值显示 `0`。数据来自最新 MVU 复读，不使用旧缓存决策。

### 4.2 商品分类

首版建议只开放结构明确、可以放入储物袋或器物的类别：

| 类别 | 写入目标 | 首版说明 |
| --- | --- | --- |
| 器物 | `主角.器物` | 武器、防具、饰品、辅助器物 |
| 丹药 | `主角.储物袋` | 数量型消耗品 |
| 灵药/丹材 | `主角.储物袋` | 灵草、灵果、妖丹等 |
| 炼器材料 | `主角.储物袋` | 灵矿、异金、兽骨、灵木等 |
| 符箓/阵材 | `主角.储物袋` | 符纸、符墨、阵旗、阵材等 |
| 修炼杂项 | `主角.储物袋` | 不产生永久变量效果的普通物资 |

功法、已学习术法、血脉、永久属性、活体灵兽、任务关键物品暂不出售。

### 4.3 商品生成

商品生成必须使用独立设置与严格结构化输出。建议设置：

```text
启用自动更新：默认关闭
更新间隔：默认 3 个稳定 AI 正文楼层
单轮商品数：默认 6，范围 1..20
保留上限：默认 30，范围 5..100
```

模型输入只包含必要资料：万宝楼相关世界书、规则/背景条目和有限近期正文。万宝商行不得为了生成商品新增对其他 `stat_data` 字段的读取；剧情时间、地点或境界如确有需要，只能从已经授权的非 MVU 上下文取得，拿不到时安全省略。

模型输出至少包含：稳定 ID、名称、类别、品阶、描述、效果、价格品级、价格数量、购买写入目标、是否可叠加。脚本必须校验类别、数量、文本长度、价格非负、ID 唯一和写入目标白名单。

### 4.4 货币适配

模式：

```ts
type CurrencyStorageMode = 'auto' | 'legacy-bag' | 'combat-separate';
```

战斗版使用四个直属数字字段。原版使用储物袋中的灵石条目。

原版标准键：

```text
极品灵石
上品灵石
中品灵石
下品灵石
```

识别结果：

```ts
type CurrencyResolution = 'exact' | 'confirmed' | 'candidate' | 'missing';
```

- `exact`：精确标准键且 `{ 数量: 非负有限数字 }`；
- `confirmed`：用户为当前 chat 明确绑定的候选键，交易前仍须复验；
- `candidate`：仅供设置页提示，禁止交易；
- `missing`：显示 0，扣款失败；收款创建行为必须等固定模板确定后才能启用。

候选匹配允许安全规范化空格和明确的“（货币）”展示后缀；含“矿、袋、碎片、兑换券、原石”等名称必须排除。模糊匹配不得自动确认。

### 4.5 购买事务

```text
捕获 chatId / messageId / contextRevision
→ 重新读取最新 MVU 楼层
→ 解析货币模式和余额
→ 验证商品、数量、目标和余额
→ 克隆完整 stat_data
→ 仅在授权路径内扣款并增加/合并资产
→ 再次检查上下文未变化
→ 一次 replaceLatestStatData 写回
→ 复读同一楼层
→ 同时核对余额和资产结果
→ 成功后写交易展示记录并 sendContext
```

余额不足、候选未确认、上下文变化、重复提交、写回失败或复读不一致时，不得报告成功。

### 4.6 出售事务

```text
重新读取最新 MVU
→ 从储物袋/器物投影可出售项
→ 排除四档灵石和候选货币条目
→ 验证数量、状态和用户确认
→ 计算已校验报价
→ 同一次克隆中减少/删除资产并增加灵石
→ 写回并复读
```

首版默认禁止出售：已装备、绑定、任务物、不可交易物、结构无法识别的条目。若现有 schema 没有可靠状态字段，采用保守策略并在 UI 明示。

## 7. 风险与止损

| 风险 | 处理 |
| --- | --- |
| 原版模型改名 | 候选提示＋用户绑定；歧义闭锁 |
| 同名普通物品误判货币 | 精确白名单、结构校验、排除词 |
| 缺失灵石品级 | 显示 0；扣款失败；创建模板未定前禁止对应收款 |
| 重 Roll 覆盖交易 | 真实运行验证；必要时交易前明确提示楼层风险 |
| MVU 写回覆盖未知字段 | 克隆完整对象、只改授权分支、前后深比较 |
| 双击或并发交易 | 单事务锁、上下文令牌、按钮禁用 |
| 跨存储不原子 | MVU 成功后才写展示记录；资产真源永远是 MVU |
| AI 价格失控 | 数值范围、境界/品阶约束、用户确认 |

同一事务问题修复 2～3 轮仍不稳定时停止补丁，回到适配器或事务边界重新设计。
