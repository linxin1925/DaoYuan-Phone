# 道渊小手机 V0.9 · Luna 开发工作流

> 用途：切换 Luna 后直接从本文件继续。本文规定执行顺序、检查命令、证据和交接格式。

## 1. 每次会话开工顺序

1. 完整读取：
   - `项目记忆.md`
   - `开发实施记录.md`
   - `使用说明.md`
   - `道渊前端桌宠/docs/维护者扩展开发手册.md`
   - `CHANGELOG.md`
   - `docs/v0.9/实施计划.md`
   - 本文件
2. 运行 `git status --short --branch`。
3. 确认工作位置是基于 `c161ba5` 的 V0.9 独立分支/worktree。
4. 确认源码目录是 `道渊前端桌宠/integration/tavern-helper-pet`。
5. 复述本轮目标、红线和验收；只实施一个纵向切片。

若当前仍是 `ziwei-live2d`、`20ca093` 或含 V1.5 Vue 预览文件，停止写代码，先建立正确基线。

## 2. 建立工作分支

本步骤会改变 Git 状态，执行前向用户说明，但不推送：

```bash
git worktree add <新目录> -b codex/v0.9-wanbao c161ba5
```

禁止在包含 PSD 和 V1.5 未跟踪文件的现有工作树中直接切换、清理或覆盖。

进入新 worktree 后记录：

```bash
git rev-parse HEAD
git status --short --branch
shasum -a 256 道渊前端桌宠/道渊小手机V0.8.json
```

预期提交：`c161ba50cdb775183e3b9d8ddb1236480bc75cbf`。

预期 V0.8 SHA-256：

```text
09c00d08eff617be3431bdd18646fcae00fd42035223a06e5047dce3c41c5186
```

## 3. 基线验证

在正确源码目录执行：

```bash
./node_modules/.bin/vue-tsc --noEmit
node scripts/validate-fixtures.mjs
node scripts/validate-trends-ui.mjs
node scripts/validate-forum-news-ui.mjs
node scripts/validate-v08-regressions.mjs

node scripts/package-candidate.mjs
```

注意：V0.8 的打包脚本会写 V0.8 文件。建立 V0.9 工作线后，应先修改打包目标为 `道渊小手机V0.9测试.json`，再执行候选打包；不得在原工作树覆盖正式 V0.8。

## 4. 固定开发循环

每个阶段都执行：

```text
读取当前契约与调用方
→ 增加最小 fixture/失败样例
→ 实现一个纵向行为
→ 运行最小相关检查
→ 检查授权字段边界
→ 运行完整回归
→ 生产构建
→ 生成 V0.9 测试 JSON
→ 检查 JSON 内容一致性
→ 必要时导入真实 SillyTavern 验收
→ 更新进度与交接
```

禁止一次同时完成商品生成、购买、出售和自动调度。

## 5. 推荐任务顺序

### 任务 A：打包护栏

- 版本改为 `0.9.0-test`；
- 名称改为“道渊小手机V0.9测试版”；
- ID 使用测试 ID，避免覆盖 V0.8 运行实例；
- 输出固定为 `道渊小手机V0.9测试.json`；
- 新增脚本检查禁止写入 V0.8 正式路径。

完成证据：打包只产生 V0.9 测试文件，V0.8 hash 不变。

### 任务 B：数据契约与 fixture

- `WanbaoItem`、`WanbaoData`、设置和摘要 schema；
- 原版标准灵石、改名候选、缺失品级、歧义候选；
- 战斗版四档数字；
- 数组/对象型储物袋兼容；
- 空器物、唯一器物、可叠加材料。

完成证据：脏数据回退且不产生可交易假余额。

### 任务 C：只读货币适配与余额 UI

- 先实现 `readBalances` 和 `detect`；
- UI 固定显示四档；
- 原版候选映射只提示；
- chat 切换后映射隔离；
- 不实现任何写回。

完成证据：原版、战斗版真实楼层余额与 UI 相同。

### 任务 D：商行商品与设置

- 桌面入口、列表、详情、设置；
- 独立 API 设置；
- 更新间隔、单轮数量、保留上限；
- 手动生成先于自动生成；
- 严格结构验证和错误提示。

完成证据：非法 AI 返回不覆盖旧商品。

### 任务 E：自动生成调度

- 复用 V0.8 仙网的稳定尾楼补偿与按楼去重思想；
- 商行拥有独立 counter 和 processed/triggered 集合；
- 重 Roll 是否重新生成必须有明确设置，默认不产生额外请求；
- 写入后 `sendContext()`。

完成证据：连续楼层、重 Roll、删除楼层和手动更新互不重复。

### 任务 F：购买

- 首先只对 fixture 实现纯函数事务；
- 再接 `MvuChannelTool`；
- 战斗版真实测试通过后接原版；
- 每次只允许一个交易；
- 复读确认余额和物品同时变化。

完成证据：余额不足零写入；成功交易只改授权路径。

### 任务 G：出售

- 候选货币和四档标准键不得出现在出售列表；
- 数量、唯一器物、禁止状态分别测试；
- 出售报价必须用户确认；
- 减少资产与增加余额同次写回。

完成证据：部分/全部出售和失败回滚通过。

## 6. MVU 事务模板

所有交易统一使用以下顺序，不允许 UI 直接写变量：

```text
UI BridgeAction
→ 宿主校验 payload
→ 捕获上下文令牌
→ mvuChannel.readLatestVariables()
→ 解析授权分支
→ 纯函数计算 nextStatData
→ 深比较未授权字段
→ mvuChannel.replaceLatestStatData(nextStatData, expected)
→ 复读同一楼层
→ 验证后发送 STATUS 与 sendContext()
```

未授权字段深比较至少覆盖：

```text
删除允许变化的路径后，before 与 after 必须深度相等。
```

禁止先扣款后第二次写入物品，也禁止失败后用第二次“补偿写入”猜测恢复。

## 7. 原版候选映射工作流

1. 精确键＋数字数量 → `exact`。
2. 安全规范化后符合品级灵石 → `candidate`。
3. 排除名称含矿、袋、碎片、兑换券、原石等条目。
4. 候选只展示，不进入余额或交易。
5. 用户明确选择后按 `chatId` 保存映射 → `confirmed`。
6. 每次交易前复验键、结构和数量。
7. 映射失效、候选重复或标准键重新出现 → 关闭对应品级交易并要求重选。

不得自动“选择最像的一个”。

## 10. 真实 SillyTavern 验收矩阵

### 10.1 两版共同

- 新聊天、现有聊天；
- 刷新页面；
- 切换 chat；
- 新 AI 楼层；
- 重 Roll；
- 编辑和删除楼层；
- MVU 未就绪；
- 交易时切换 chat；
- 双击交易；
- 脚本关闭和重新开启。

### 10.2 原版

- 标准三档存在、下品缺失；
- 四档完整；
- 非标准候选名；
- 两个候选造成歧义；
- 用户确认映射后交易；
- 映射条目被模型改名后闭锁。

### 10.3 战斗版

- 四档直属字段均为 0；
- 单品级余额充足/不足；
- 储物袋购买；
- 器物购买；
- 出售后直属字段增加。

### 10.4 UI

- 320×568、360×800、390×844、430×932；
- 长商品名、长描述、四档大数字；
- 确认弹窗和错误提示；
- computed style、bounding rect 和实际截图；
- 交易后余额与资产可见刷新。

## 11. 安全失败文案

至少区分：

```text
未检测到灵石结构
发现疑似灵石，请先确认映射
灵石映射已失效
余额不足
物品结构不支持交易
交易期间聊天或楼层已变化
MVU 写回失败
写回后复读不一致
商品生成失败，旧商品已保留
```

不得把 API 失败、余额不足和存储失败混成同一个“操作失败”。

## 12. 提交和交接

未经用户确认不提交、不推送。准备提交时先列出：

- 目标分支；
- 计划提交的文件；
- 未跟踪文件；
- 完整检查结果；
- 真实酒馆尚未验收项。

每次 Luna 会话结束更新一段交接：

```text
本次目标：
完成内容：
修改文件：
运行检查及结果：
真实运行证据：
未解决问题：
下一步第一条命令/文件：
V0.8 hash 是否保持：
是否提交/推送：否
```

“离线通过”与“真实酒馆通过”必须分开写，不得合并成一句“全部通过”。
