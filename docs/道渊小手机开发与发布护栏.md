# 道渊小手机开发与发布护栏

本文档约束道渊小手机的开发、打包、Git 推送和 CDN 发布流程。目标是避免未经复核的代码进入 `main`，以及避免测试包、内置版、外链版或 CDN 文件相互覆盖。

## 一、推送的二次确认规则

用户第一次说“推送”“发布到 main”“更新 CDN”等，只表示开始准备发布，不代表可以立即执行提交或推送。

发布前必须按顺序完成：

1. 确定本次发布范围、目标分支、远程仓库和产物名称。
2. 对本次范围进行代码审查并运行相应验证。
3. 向用户完整报告审查结果和未验证边界。
4. 列出准备提交的文件，并明确说明将执行的动作。
5. 询问：`审查已完成，是否现在提交并推送到 <远程>/<分支>？`
6. 仅在用户看到报告后再次明确同意，才可执行提交和推送。

如果二次确认后又修改了代码、重新生成了产物、调整了提交范围，或更换了分支/远程仓库，必须重新审查并重新确认。

## 二、代码审查最低检查项

每次推送前至少检查以下内容：

- 审阅相对当前 `HEAD` 的完整差异，确认没有无关文件、调试代码或意外删除。
- 按严重程度报告问题：P0 阻断、P1 高风险、P2 一般问题、P3 建议。
- 检查运行时生命周期、重复加载、事件解绑、全局变量冲突和内置版/外链版共存行为。
- 检查设置迁移、默认值、拖拽位置、抽屉/浮窗模式及窄屏兼容。
- 检查远程代码加载、动态导入、URL 校验、缓存策略和失败回退。
- 扫描密钥、令牌、Cookie、个人路径及不应公开的日志或数据。
- 执行项目现有的类型检查、构建、自动化测试及 `git diff --check`。
- 对生成的酒馆 JSON、CDN 运行时和源码进行一致性检查，避免只修改源码但漏打包。
- 涉及真实 SillyTavern 行为时，区分本地预览证据与真实酒馆验证；未做的验证必须明确写出。

存在 P0 或未解决的 P1 时，不得请求推送确认，应先修复或由用户明确决定如何处理。

## 三、发布动作必须分开授权

以下动作互不等价，应分别说明并取得对应授权：

- 创建 Git 提交。
- 推送分支。
- 合并或直接更新 `main`。
- 创建或移动 Git 标签。
- 创建 GitHub Release。
- 更新 CDN 运行时或版本清单。
- 将测试版替换为正式版。

禁止强制推送。禁止用测试产物覆盖用户要求保留的正式或独立测试文件。

## 四、审查报告模板

```text
审查结论：通过 / 有条件通过 / 阻断
审查发现：按 P0—P3 列出；没有问题也要明确写“未发现阻断项”
已验证：列出实际执行的检查及结果
未验证边界：列出尚未在真实环境复现或验证的内容
拟提交文件：逐项列出
目标：<remote>/<branch>
后续动作：commit / push / tag / Release / CDN 更新

审查已完成，是否现在执行上述提交和推送？
```

## 五、当前项目的额外约束

- `道渊小手机V1.2测试.json`、显示模式测试包和 CDN 外链版必须保持独立身份，不能无提示相互覆盖。
- CDN 外链版应保留可诊断的加载错误，并确保回退地址不会静默加载错误版本。
- 更新自动版本清单时，清单引用的运行时提交和校验值必须与已推送文件一致。
- 鲸鱼娘、手机运行时和设置面板的改动必须检查重复初始化与旧实例清理，避免黑框、双实例或无法显示。
